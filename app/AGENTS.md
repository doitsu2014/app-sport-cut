# AGENTS.md — Flutter client (`app/`)

Applies to everything under `app/`. The repository-root `AGENTS.md` applies too;
this file adds client-specific detail. If the two disagree, this file wins inside
`app/`.

## Ground rules

- Keep `flutter analyze` clean; lints come from
  `package:flutter_lints/flutter.yaml`.
- Talk to the engine only through `app/lib/src/bridge/sportcut_engine.dart`.
  Feature code must not import `bridge/generated/` directly.
- Generated bindings under `lib/src/bridge/generated/` are never hand-edited and
  never committed — regenerate them with `tools/generate-bridge.sh` from the
  repository root.
- No network access in product code paths.

## Commands

```bash
tools/generate-bridge.sh         # once, and after any engine API change
tools/build-engine-lib.sh        # engine library the bindings load

cd app
flutter pub get
flutter analyze                  # static analysis
flutter run -d macos             # desktop run
```

Set `SPORTCUT_FLUTTER_BIN` to the directory containing the `flutter` executable
when the SDK is not on `PATH`. `tools/preflight.sh --profile macos` reports what
is missing for the macOS client.

## Structure

```
lib/
  main.dart                  startup: load the engine, inject it, run the shell
  src/
    app/                     shell: routing, theme, dependency injection
    bridge/
      sportcut_engine.dart   hand-written typed wrapper over the engine
      generated/             generated by tools/generate-bridge.sh (not committed)
    features/<feature>/      domain/, data/, presentation/ as needed
```

Reuse the existing patterns rather than introducing new ones:

- navigation is the plain named route table in `src/app/router.dart`;
- shared state and dependency injection use Riverpod providers
  (`src/app/di.dart`), with `sportcutEngineProvider` overridden in `main.dart`;
- features depend on repository interfaces (`features/library/domain/`) instead
  of concrete implementations.

## Working agreement

Implement first. Do not add or run widget tests unless the user explicitly asks;
verify with `flutter analyze`. Run `flutter test` only when the user asks to
verify, close, or archive an OpenSpec change.
